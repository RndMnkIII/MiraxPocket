# MiraxCore — Mirax (Current Technology, 1985) for the Analogue Pocket

Fidelity-first FPGA / SystemVerilog reimplementation of the arcade game **Mirax**
for the **Analogue Pocket** (openFPGA / Cyclone V). MAME's `misc/mirax.cpp` is used
only as a reference oracle; the PCB photos and datasheets are the primary sources.

All game ROMs are **baked into the bitstream** — there is no APF data-slot load step.
The game is ready as soon as the core is loaded.

## Architecture

| Block            | Implementation                                                        |
| ---------------- | --------------------------------------------------------------------- |
| Main CPU         | Z80 (tv80 / T80)                                                       |
| Sound CPU        | Z80 (tv80 / T80)                                                       |
| PSG              | AY-3-8912 (jt49)                                                       |
| Program decrypt  | Encrypted-program descrambler (verified 0 mismatches over 48 KiB vs MAME) |
| Tilemap          | Per-column scroll, 2-phase colorram read, lookahead fetch pipeline     |
| Sprites          | Line-buffer engine, per-line FSM on the 48 MHz clock                   |
| Palette          | PROM-driven DAC                                                        |

Top level: `core_top.v` (openFPGA) → `mirax_pocket.sv` (the game) → `mirax_main`,
`mirax_sound`, `mirax_video`, `mirax_clocks`.

## Clocking

The board ran off a single **12.000 MHz** crystal. On FPGA everything is a clean
divide of one fast clock, gated with clock-enables (`mirax_clocks.sv`):

| Signal      | Rate      | Use                          |
| ----------- | --------- | ---------------------------- |
| `clk_sys`   | 48.000 MHz| core render + sprite FSM     |
| `ce_3m`     | 3.000 MHz | main/sound Z80 + AY          |
| `ce_pix`    | 6.000 MHz | pixel advance (see below)    |
| `clk_vid`   | 6.000 MHz | **APF pixel clock** (PLL)    |

The **pixel clock is 6.000 MHz generated by the PLL** (`video_rgb_clock = clk_vid`).
The core renders in the 48 MHz domain, so pixels are advanced with a `ce_pix` strobe
that is **aligned to the rising edge of `clk_vid`** (edge detected inside the 48 MHz
domain). This keeps the rendered pixel phase-locked to the clock the APF scaler
samples on — without it, a free-running 6 MHz enable has an arbitrary phase versus
`clk_vid` and the scaler latches pixels mid-transition (the classic "orange noise").

```verilog
reg [2:0] vdsync;
always @(posedge clk_sys) vdsync <= {vdsync[1:0], clk_vid};
wire ce_pix = ~vdsync[2] & vdsync[1];   // one pulse per clk_vid rising edge
```

## Video (Analogue Pocket LCD)

- Active raster **256 × 240**, vertical (**ROT90**) game.
- `video.json`: `width 256, height 240, rotation 90, aspect 3:4`.
- APF output stage: OpenGateware `video_mixer` (runs on `clk_vid`), which re-times
  the core signals into the APF protocol (single-cycle HS/VS, DE, SKIP, RGB=0 in
  blank, VS→HS 3-cycle gap, DE↔HS 1-cycle gaps).

### Synthetic APF sync (why the scaler locks)

The APF scaler shows **"sync internal @ 60 Hz"** when it can't detect a valid
VSync/HSync. The `video_mixer` emits HS only on the **rising edge** of `core_hs`
and **suppresses** it for one cycle after DE falls. If the core's raw `hsync` edge
lands on the hblank/DE boundary, HS is killed every line and the scaler never locks.

Because `hblank`/`vblank` are solid (the game runs and the vblank IRQ fires), the
Pocket sync is **synthesized from the blanking** in `core_top.v`, offset a few
cycles into the blank so its rising edge can never collide with the mixer's guards:

```verilog
localparam [3:0] HS_OFFSET = 4'd4;   // cycles into hblank
localparam [3:0] VS_OFFSET = 4'd4;   // cycles into vblank
// ... generates core_hs_apf / core_vs_apf from core_hb / core_vb on clk_vid
```

The mixer is fed `.core_hs(core_hs_apf), .core_vs(core_vs_apf)`.

### Signal Tap checklist (sample clock = `clk_vid`)

- `video_vs` → 1 pulse per frame
- `video_hs` → 1 pulse per line
- `video_de` → 256 cycles/line, 240 lines
- Also confirm the PLL `clk_vid_90` tap is 6 MHz with a real **+90°** shift.

## Audio

`mirax_sound` outputs 10-bit unsigned PSG audio (DC ≈ 512). It is converted to
signed 16-bit mono and duplicated L/R:

```verilog
wire signed [15:0] snd16 = $signed({1'b0, snd} - 11'sd512) <<< 6;
```

In `core_top.v` this feeds the APF I²S serializer (MCLK = 12.288 MHz, SCLK = MCLK/4,
16-bit MSB-first, 2-FF CDC into the audio-clock domain).

## Controls

MAME input map (active-high), P1 @ `0xF000`. openFPGA `cont_key` bits map straight in:

| Function | Mirax bit (P1) | openFPGA `cont_key` |
| -------- | -------------- | ------------------- |
| UP       | 5              | 0                   |
| DOWN     | 0              | 1                   |
| LEFT     | 2              | 2                   |
| RIGHT    | 3              | 3                   |
| FIRE     | 4              | 4 (A)               |
| START1   | 1              | 15 (Start)          |
| COIN1    | 6              | 14 (Select)         |
| COIN2    | 7              | —                   |

Single action button. (`pocket_input_map` performs the translation.)

## Building

1. Open the openFPGA project in **Quartus** (Cyclone V, Analogue Pocket).
2. Ensure the ROM `.hex` files are present next to the sources:
   `prog.hex`, `audio.hex`, `tiles_p0/1/2.hex`, `sprites_p0/1/2.hex`, `proms.hex`
   (produced by the ROM packer from your own Mirax ROM set — not distributed here).
3. Confirm the PLL taps: `outclk_0 = clk_vid (6 MHz)`, `outclk_1 = clk_vid_90
   (6 MHz @90°)`, `outclk_2 = clk_sys (24 MHz)`, `outclk_3 = clk_sys48 (48 MHz)`,
   `outclk_4 = clk_sys48_90`.
4. Compile → package the core per Analogue's core-packaging docs.

## Simulation

- **Icarus Verilog** and **QuestaSim** (`tb_questa.sv`) run the full core.
- The harness dumps numbered frames (`frames/frame_00001.ppm`, …) and captures
  audio to **WAV** (or raw PCM).
- Frame-compare and per-block testbenches (`tb_sprite.sv`, `tb_video_synth`, …)
  validate against the MAME reference.

## Tools: frames → video (with sound)

`frames2video.bat` turns the numbered frame dump into an MP4 and (new) **muxes the
audio captured by the simulation**. Requires `ffmpeg` on `PATH`.

```
frames2video.bat [indir] [fps] [scale] [out] [rot] [ext] [aud] [arate] [ach]
```

| Arg     | Default     | Meaning                                                        |
| ------- | ----------- | -------------------------------------------------------------- |
| `indir` | `frames`    | frame folder                                                   |
| `fps`   | `60`        | input frame rate (arcade native)                               |
| `scale` | `3`         | integer pixel upscale (256×240 → 768×720)                      |
| `out`   | `mirax.mp4` | output file                                                    |
| `rot`   | `0`         | `0 / 90 / 180 / 270` — Mirax is vertical, use `90` for upright |
| `ext`   | `ppm`       | `ppm` or `png`                                                 |
| `aud`   | `mirax.wav` | audio from the sim; `.wav` (header-read), `.pcm/.raw` (s16le), or `none` |
| `arate` | `48000`     | sample rate for **raw PCM** (ignored for `.wav`)               |
| `ach`   | `1`         | channels for **raw PCM** (ignored for `.wav`)                  |

The core's audio is **signed 16-bit little-endian**, so a raw dump is muxed with
`-f s16le`. WAV is read from its header. Audio is encoded as AAC (`-b:a 192k`) and
`-shortest` trims to the shorter stream. With no audio file present (or `aud=none`)
it produces a silent video exactly as before.

**Examples**

```bat
REM WAV from the sim, upright:
frames2video.bat frames 60 3 mirax.mp4 90 ppm mirax.wav

REM raw mono PCM s16le at 48 kHz:
frames2video.bat frames 60 3 mirax.mp4 90 ppm sound.pcm 48000 1

REM silent:
frames2video.bat frames 60 3 mirax.mp4 90 ppm none
```

> **Sync note:** for raw PCM the `arate` **must** match the rate at which the
> testbench wrote samples, or the audio will drift against the video. WAV carries
> its rate in the header and needs no `arate`.

## Analogizer / CRT output

The core also drives the Analogizer path (analog RGB/CRT via SNAC). That path is
independent of the Pocket LCD and, in the current `core_top.v`, its clocking
(`i_clk`/`video_clk`/`ce_pix`) still needs review before analog output is validated
— the Pocket LCD path is the one that is wired and tested.
